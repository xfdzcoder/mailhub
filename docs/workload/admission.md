# Distributed work admission

API sessions and account-access predicates remain the interactive authority. Periodic sync and old queued jobs use an explicit DB lookup of account ownership; search follows email→account, summary follows its persisted run and current membership. Queued user/org claims are not admission proof. Summary execution also reloads the persisted run's owner and label.

Inventory: initial/historical sync enters partitioned Bull queues, search indexing enters search-index from both ingestion paths, summaries and their webhook notification fanout enter email-summary. SMTP/Gmail/Graph sending stays synchronous. Draft writes, IMAP EXISTS fetch/reconciliation and Gmail periodic polling acquire shared direct-work leases. Idle listener establishment and long-lived connections are not bounded by these work slots; startup has a separate local fanout bound. Account push notifications and rule forwarding also acquire trusted-account leases; push fanout is serial and capped at 100 subscriptions per notification. Other interactive IMAP operations remain follow-up coverage requirements.

Defaults (environment variables, positive integers): WORK_PRINCIPAL_QUEUED=32, WORK_ORG_QUEUED=128, WORK_GLOBAL_QUEUED=4096 outstanding reservations; WORK_PRINCIPAL_ACTIVE=2, WORK_ORG_ACTIVE=4, WORK_GLOBAL_ACTIVE=16 concurrent operations across queues/processes. WORK_RESERVATION_BYTES=1048576 bytes per staged unit; WORK_{PRINCIPAL,ORG,GLOBAL}_STAGED_UNITS=32/128/4096. Payloads use rounded-up UTF-8 JSON bytes, minimum one unit; queue payloads may contain at most one unit and should only contain references. Direct send/draft requests reserve their serialized payload. An individual reservation can use at most 128 units. Lua reconciliation examines at most 256 stale members per scope per admission; remaining stale members are processed on later calls. These measure staging, not decoded MIME memory, disk bytes, CPU time or provider connection counts. Decoding/stream bounds belong to #23's follow-up. See storage-prerequisite.md for the separate blocking storage migration.

WORK_QUEUE_LEASE_MS=86400000 is the admission deadline for queued work. WORK_ACTIVE_LEASE_MS=120000 recovers abandoned active slots, renewed every third of that interval. Redis TIME avoids clock skew for atomic reservations. Queued permits survive while the corresponding Bull job exists; expired permits are reconciled against persisted finishedOn/existence on subsequent admission. This prevents an offline worker's backlog from accumulating a fresh allowance every day. No queue reset/drain is used. This version requires standalone Redis: cross-queue reconciliation reads Bull keys and is not Redis Cluster compatible.

Enqueue failures keep a conservative reservation because a timeout may conceal a successful enqueue. Missing jobs release on lease expiry. Completed/terminal work releases idempotently, failed attempts retain queued permits, crashed worker active slots expire. Old jobs resolve DB ownership and re-admit; jobs older than the queue deadline terminally fail instead of silently running outside budgets. Producer retries are bounded at three with exponential 5s backoff, summaries/sends at one to avoid repeating external side effects. Worker contention delays 5–10 seconds with jitter without consuming business retries, bounded by the queue deadline. Terminal queue retention: 100 completed/one hour and 500 failed/one day; search and initial-sync completion removes jobs immediately so subsequent updates can schedule again. Explicit job removal recovers through reconciliation rather than immediate release.

Redis errors fail closed: API admission throws a typed unavailable error (send/draft/summary return 503; quota denial returns 429); no direct summary fallback. Admission connections have no offline command queue and 1.5s command timeout. Renew failures are reported after the operation; underlying libraries currently lack a common cooperative cancellation/fencing contract, so already-running provider work can outlive a lease during Redis failure or a process pause. This is an outstanding strict-concurrency limitation, not an exactly bounded runtime guarantee.

Per-principal and organization caps below global capacity prevent one tenant from taking every slot. Each queue lane also permits at most one active job per organization. Sync workers run at least two Bull processors (even if SYNC_WORKER_CONCURRENCY is one), so a tenant with a slow sync cannot occupy every processor in its partition. Search and summary workers already have multiple processors. Busy jobs yield worker slots when denied rather than sleeping inside a processor. This provides capacity isolation; it is not strict weighted round-robin scheduling or a latency guarantee with arbitrary numbers of competing tenants. Configuration is clamped to keep global limits at least two, organization limits at most half the global allowance, and principal limits at most the organization allowance. Provision at least two worker slots. Periodic skipped work is retried on its next ordinary poll, without recursively scheduling retries. Bootstrap continues after one tenant's enqueue denial.

Send fingerprints are recorded before provider delivery in a bounded per-principal/org Redis set: 1000 unique sends per principal/organization pair, 10000 per organization, and 100000 globally, retained for seven days. All three caps are checked atomically. Identical payload/account attempts return 409 and require delivery investigation, including failures after SMTP acceptance or partial RCPT acceptance. This conservatively prevents duplicate delivery but also blocks intentional identical sends for seven days; no exactly-once claim is made, and Redis data loss or expiry loses this protection. Durable send idempotency requires a separately reviewed outbox/receipt ledger. Never automatically retry an uncertain send.

Before rollout, inventory existing queues without draining them, size budgets against observed account counts/backlogs, and coordinate API/worker adoption. Mixed old processes can bypass admission; deploy all producers/consumers together in a reviewed rollout. Existing retained jobs may temporarily suppress rescheduling by deterministic job ID. No deployment/environment values are changed here. This slice has explicit outstanding storage, fencing and coverage limitations; do not close #47 until these are resolved and reviewed.

Integration tests opt in with WORKLOAD_TEST_REDIS_SERVER pointing to an isolated redis-server executable. Tests create only disposable Unix-socket Redis instances and small synthetic Bull queues, never use REDIS_URL or live mail.

Validation: Node 24.22.2 lint (zero errors; 83 existing warnings), TypeScript, all 817 tests across 117 suites with both Redis opt-ins enabled, and production build; disposable real Redis atomic scripts and two independent Bull workers. Ownership uses synthetic Prisma fixtures; no PostgreSQL service/database integration was run. These are not evidence of durable storage enforcement or crash-safe SMTP receipts.
